## 三、架构与技术资产（摘自代码审查报告，仍有参考价值）

### 架构总览
- **后端**：Spring Boot 3 + RuoYi 框架改造，业务模块 `ruoyi-system`（book/reader/borrow/reserve/purchase/cms/banner）
- **前台**：`ruoyi-ui/public/` 纯静态页（12 个 HTML + site.css），fetch 调 `/prod-api` 公开接口

### 核心业务流程
- **报名**：`borrowByCard`（FOR UPDATE 锁 + CAS 条件更新防并发）
- **候补**：`reserveByCard`（名额满排队，`BorrowTask.reserveExpireCheck` 超时自动推进下一位）
- **入驻申请**：`purchase/apply`（登录后自动挂 reader_id，个人主页可查状态）
- **订单**：`ShopOrderServiceImpl`（状态机 0→1→2，加锁顺序 成员→服务）

### 技术实践亮点
- 前台 XSS 防护：全部插值过 `esc()` + 正文 textContent 白名单渲染
- SQL 注入：mapper 全 `#{}`，orderBy 双白名单
- 证号 SecureRandom 8 位不可预测 + 登录防枚举 + IP 频控
- 数据库快照：`.githooks/pre-commit` 自动导出（已排除 PII 表）

### 🟠 中等（正确性 / 公网加固）

**M1. 挂失补办不同步候补表的证号快照**
- `ReaderServiceImpl.reissueCard()` 只更新了 `borrow_record.card_no`（updateCardNoSnapshot），没动 `book_reserve.card_no`。换新证号后：
  - 个人主页「我的候补」按新证号查 → 旧候补记录消失；
  - `reserveByCard` 重复候补校验按 card_no → 校验失效，可重复候补；
  - `cancelByCard` 用 `reserve.getCardNo()` 做归属比对 → 旧候补无法取消。

**M2. 会话过期被静默吞成"暂无记录"**
- 会话 TTL 30 分钟且无滑动续期。profile.html 的 `loadBorrows/loadReserves/loadPurchases` 与 services.html 的 `queryMyBorrow/queryMyReserves` 均不检查 `d.code`：过期后 data=null 被当空列表渲染成"暂无××记录"，用户误以为数据丢失，而非引导重登。

**M3. 频控 IP 取值可伪造**
- 登录/注册/补办/入驻申请频控基于 `IpUtils.getIpAddr()`（取 XFF 第一段），nginx `$proxy_add_x_forwarded_for` 为追加不覆盖 → 客户端自带伪造 XFF 即可轮换绕过"30 分钟 5 次"。演示可接受；公网部署需改信任 nginx 追加后的最后一段或 `$remote_addr`。⚠️

**M4. 后端 8080 直映射公网 + Swagger 匿名开放**
- compose 发布 `"8080:8080"`，同时 SecurityConfig 对 `/swagger-ui/**`、`/v3/api-docs/**` permitAll 且生产配置 `springdoc.swagger-ui.enabled: true` → 可绕过 nginx 直接浏览全量 API 文档。建议生产关 springdoc 或去掉端口映射。
