## 二、核心业务流程（状态机）

### 1. 借阅：`BorrowRecordServiceImpl`
```
0=借出中 → 1=已归还 ；2=已逾期（查询时动态计算为主，每日 0 点任务落库）

借书：锁读者行 → 锁图书行（锁序统一：读者→图书）→ 校验链（在架/库存/读者正常/
      无欠费/未重复借/未超上限/可借预约优先）→ 快照写入 → 原子扣库存 → 插入 → 预约完成 → 邮件
还书：CAS(updateStatusIfCurrent) 抢转换权 → 仅赢家回补库存 → 同步催还公告 → CAS 推进预约队列
续借：行锁 → 校验（上限 book.borrow.renewLimit，默认 1 次）→ dueDate +30 天（硬编码）
```
- 关键不变式：**先 CAS 抢状态转换权、只有赢家才回补库存**——并发双还书不会双回补。

### 2. 订单：`ShopOrderServiceImpl`
```
0 待付款 → 1 已完成 / 2 已取消 / 3 已收款 ；3 已收款 → 1 已完成；其余流转一律拒绝
实现：读旧状态 → 白名单校验 → updateStatusIfCurrent(orderId, from, to) CAS → 仅 0→2 回补库存
前台取消 cancelByCard：直接 CAS（不走 updateShopOrder 避免二次回补）
```
- 订单号唯一索引 `uk_order_no` + 随机后缀防同毫秒重号。

### 3. 预约：`BookReserveServiceImpl` + 还书 + `BorrowTask`
```
0=预约中 → 1=可借 → 2=已完成（借出时置）；0/1 → 3=已取消
创建：仅库存=0 可约；锁读者行→锁图书行→查重复→插入
推进：还书时 CAS 推进最早"预约中"为"可借"（失败取下一位）；每日 8 点超时（expireDays 默认 2 天）
      取消"可借"超时未取并推进下一位，防队列卡死
```

### 4. 罚款：`FineService`
```
罚款 = max(0, (逾期天数 - 免罚天数)) × 0.10 元/天（book.fine.perDay 可配，HALF_UP 两位小数）
欠费拦截：借书前 checkNoUnpaidFine → 拒绝；还书自动结算；收银收款置 fine_paid='1'
```

### 5. 库存联动（全书核心一致性问题）
- 借出/下单：行锁内校验（友好提示）+ `update stock=stock-#{q} where stock>=#{q}`（原子兜底）
- 归还/取消：仅 CAS 赢家 `restoreStock(+1)`
- 上下架/删除图书：与借阅共享同一把 book 行锁，消除"幽灵预约/幽灵订单"竞态

### 6. 定时任务（Quartz，`BorrowTask`，sys_job 注册）
| 任务 | 时间 | 行为 |
|---|---|---|
| `updateOverdueStatus` | 每天 0:00 | 全量查借出中记录 → CAS `markOverdue` 落库逾期 → 失效统计缓存 |
| `reserveExpireCheck` | 每天 8:00 | "可借"超期 CAS 取消 + 推进下一位 |
| `remindOverdue` | 每天 9:00 | 有逾期且当天未发过 → 发布催还公告（不列读者姓名） |

### 7. 统计缓存
读路径：`stats:topBooks / topReaders / dashboard` 三键缓存 5 分钟；写路径 14 处调用 `evictAll()` 主动失效，保证缓存永不脏。

## 三、值得保留的技术实践（本项目的资产）

1. **并发正确性工程化**（显著超出若依模板）：
   - FOR UPDATE 行锁 + 统一锁序（读者→图书，批量删除前 Arrays.sort）防死锁
   - `@Transactional(isolation = READ_COMMITTED)`：解决 REPEATABLE READ 旧快照导致批量删除第 2 个起漏检
   - CAS 原子状态转换（`updateStatusIfCurrent`，borrow/order/reserve 三处）+ 原子库存条件更新
2. **快照冗余 + COALESCE 回退**：借阅/订单/预约冗余 readerName/cardNo/bookName，删除读者/图书后历史完整。
3. **回收站模式**：`book_recycle/reader_recycle` 同事务快照 + 还原（原主键被占用自动换新）+ 删除守卫。
4. **SQL 脚本幂等四重模式**：IF NOT EXISTS / INSERT...SELECT WHERE NOT EXISTS / INFORMATION_SCHEMA 判存 + PREPARE 动态 DDL / 自愈 UPDATE。
5. **安全细节**：排序字段+isAsc 双白名单防 ORDER BY 注入；BBCODE 先转义后替换 + url 协议白名单防 XSS；证号 `SecureRandom` 8 位随机（注释明确不用时间戳防推算）；登录错误提示统一防枚举；邮件异步线程池 DiscardPolicy + 启动自检。
6. **注释密度高且准确**：并发语义、锁序、快照设计、接口安全边界都有说明，是很好的维护资产。
7. 每个业务模块有配套 Mockito 单测；集成测试 full_test.py 自带前后置清理可重复跑。

### 3. 改造时的红线（本项目的隐性约定，破坏即踩坑）
1. **库存一致性**：任何扣/补库存必须遵循"行锁校验 + 原子条件更新 + CAS 赢家才回补"模式，新增状态流转必须 CAS。
2. **加锁顺序**：读者→图书；批量删除前排序；新增写路径显式 READ_COMMITTED。
3. **快照列**：新增业务表凡涉及 reader/book 引用，须冗余快照列并 COALESCE 回退。
4. **SQL 脚本幂等**：新增表用 IF NOT EXISTS，新增列用 INFORMATION_SCHEMA + PREPARE。
5. **前台接口**：新增 @Anonymous 接口须考虑频控、排序白名单、XSS 过滤（urlPatterns /system/* 已覆盖）。
6. **状态常量**：用 `BizStatus`，禁止魔法字符串；借阅状态 "2" 的双轨语义（库中/动态）以 BizStatus 注释为准。
7. **参数化**：业务参数走 sys_config + ConfigUtil，勿硬编码（续借 30 天是现存反例）。
8. **测试**：新逻辑补 Mockito 单测（ruoyi-system 现有 12 类可参照风格）；集成测试补 full_test.py 章节。

## 六、审查结论一句话

> 业务完整度高、并发正确性打磨远超若依模板（CAS/行锁/快照/幂等 SQL 已成体系），是学习价值很高的代码库；
> 主要债务集中在前台 shop.html 单体文件（维护性与 XSS 边界）、前台会话凭据传输方式、以及若干参数化/一致性小项；
> 大幅改造最安全的切入点是：先以 H1-H6 修复 + 红线清单固化为基线，再决定功能方向。
